Prompt caching可以降低重复prefix的处理成本。支持情况、最低Token数、有效期和价格取决于模型及提供商。再次发送相同提示词不保证缓存命中。

## 价格与用量

使用准备调用的API密钥，查看 [`GET /v1/models`](/zh/models) 中的 `pricing.cache_read` 和 `pricing.cache_write`。价格遵循密钥的Service Mode，单位为每100万Token；未提供的价格可能省略。缓存写入可能比普通输入更贵，节省金额取决于Token数和后续命中。

Console的 **Logs** 显示Input、Output、Cache Read、Cache Write及最终费用。Cache Write 5m/1h明细仅在上游报告时填写；`-` 表示没有明细，而不是零。部分历史费用明细按当前价格计算，但历史总额仍保留。请参阅 [Billing](/zh/billing)。

## 提示词顺序

先放静态内容：工具定义、system prompt／文档、旧消息。最新用户消息和变化的值放在后面。时间戳或工具顺序等prefix变化可能导致未命中。

在支持的Claude路由上，为静态块添加 `cache_control`。标记不会强制命中：内容仍须满足模型和上游要求。

## Anthropic Messages

在 `system` 块中添加 `cache_control` 的示例：

```bash
curl https://api.hostlinku.com/v1/messages \
  -H "x-api-key: sk-your-api-key" \
  -H "anthropic-version: 2023-06-01" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "claude-sonnet-4-6",
    "max_tokens": 1024,
    "system": [{
      "type": "text",
      "text": "<保持不变的长指令及参考文档>",
      "cache_control": {"type": "ephemeral"}
    }],
    "messages": [{"role": "user", "content": "总结第3节。"}]
  }'
```

缓存写入时的 `usage` 示例：

```json
{
  "usage": {
    "input_tokens": 16,
    "cache_creation_input_tokens": 3601,
    "cache_read_input_tokens": 0,
    "output_tokens": 4
  }
}
```

`cache_creation_input_tokens` 统计写入，`cache_read_input_tokens` 统计读取。读取值大于零表示上游报告了缓存使用。请求不满足条件或没有缓存信息时，两者可能为零。

## OpenAI Chat Completions

对Claude模型，bridge会把content part中的 `cache_control` 转发至Anthropic内容块：

```bash
curl https://api.hostlinku.com/v1/chat/completions \
  -H "Authorization: Bearer sk-your-api-key" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "claude-sonnet-4-6",
    "messages": [
      {"role": "system", "content": [{
        "type": "text",
        "text": "<保持不变的长指令及参考文档>",
        "cache_control": {"type": "ephemeral"}
      }]},
      {"role": "user", "content": "总结第3节。"}
    ]
  }'
```

Chat Completions的 `usage.prompt_tokens` 已包含缓存Token。`usage.prompt_tokens_details.cached_tokens` 统计读取；有数据时，`cache_write_tokens` 统计写入。不要再将缓存Token加入 `prompt_tokens`。

## Agent及其他协议

已设置 `cache_control` 的应用可在指向Hostlinku后使用，但行为取决于应用版本和模型。请参阅 [IDE与Agent集成](/zh/integrations)。其他模型可能无需此标记就使用上游自动缓存，但命中和报告方式因模型而异。

`/v1/responses` 的Chat Completions bridge目前不提供显式 `cache_control` 标记。native／上游路由的自动缓存及所报告的Token仍取决于模型。要使用上述Claude标记，请选择 `/v1/messages` 或 `/v1/chat/completions`。

## 检查命中

1. 发送满足模型要求的提示词，然后查看 **Logs** 的Cache Write/Read。
2. 在上游缓存有效期内再次发送相同prefix，并检查Cache Read。
3. 比较相同模型、Service Mode及输出长度的请求。输出Token也会影响费用差异。

Cache Read仍为零时，请检查prefix、内容块大小、模型支持和有效期。用量信息与预期不符时，请参阅[支持](/zh/support)。
