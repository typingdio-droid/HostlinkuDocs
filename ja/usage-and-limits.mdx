利用は、レート制限、キーのクレジット制限、および組織の残高によって制限されます。

<a id="組織で共有する利用枠"></a>

## 組織全体のクォータ

以下のクォータは、同じ組織内のすべてのAPIキーおよびメンバーで共有されます。キーを追加したり、他のメンバーのアカウントを使用したりしても、クォータは増加しません。

| Service Mode | リクエスト/分 | 1分あたりの`input`トークン | 1分あたりの`output`トークン |
|---|---|---|---|
| Performance | 600 | 6,500,000 | 200,000 |
| Low-Cost | 600 | 6,500,000 | 200,000 |
| Dedicated | 600 | 6,500,000 | 200,000 |

<a id="その他の-endpoint-制限"></a>

## その他のエンドポイントの制限

Console、ログイン、およびチェックアウトのエンドポイント制限は、IPごとに計算され、モデルの使用クォータとは別個に扱われます。

| 範囲 | 制限 | グループ分け |
|---|---|---|
| 一般的なリミッターを備えたコンソール／パブリックエンドポイント | **120リクエスト / 60秒** | IPごと |
| 認証リミッター付きエンドポイント | **30回の試行 / 15分** | IPごと |
| GET checkout（トークン付き） | **90リクエスト / 60秒** | IPごと |
| トークン付きチェックアウトの変更 | **15リクエスト／60秒** | IPごと |

<Callout type="tip" title="429で拒否されたリクエストを再送信する前に待機してください">

リセットヘッダーまたは`Retry-After`（存在する場合）を確認してください。同時実行数を減らし、ジッターを伴う指数関数的バックオフを使用してください。休止せずにリクエストを繰り返し送信しても、制限は解除されません。

リミッターエンドポイントは、`RateLimit-Limit`、`RateLimit-Remaining`、および`RateLimit-Reset`（秒）を返します。429エラーが発生した場合は、`Retry-After`または`retry-after-ms`が返されることもあります。
</Callout>

<a id="apiキーの利用上限"></a>

## APIキーのクレジット制限

Form Consoleでは**Monthly Spending Limit**が提供されています。キー管理APIは、リセットを行わない場合、`daily`、`weekly`、`monthly`、または`null`を受け付けます。 日単位の期間の開始は00:00 UTC、週単位は月曜日の00:00 UTC、月単位は毎月1日の00:00 UTCです。[認証](/ja/authentication)を参照してください。

制限は、トークンの数ではなく、キーに記録された費用に基づいて適用されます。制限に達すると、次のリクエストは `402 PAYMENT_REQUIRED` として拒否されます。残高を追加しても、キーの制限は変更されません。

<a id="reservasi-saldo"></a>

## 残高の予約

Gatewayは、組織の残高から費用の見積額を予約し、リクエストを転送した後、アップストリームの使用量に基づいて費用を精算します。予約の残額は解放されます。使用量が利用できない場合、請求では見積額を使用できます。請求可能な使用量がない場合の失敗により、予約は解放されます。

新しいリクエストの残高は `available = balance − reserved` です。残高とキーの制限は十分である必要があります。[課金と残高](/ja/billing) を参照してください。

<a id="memantau-di-console"></a>

## Consoleでの監視

| メニュー | データ |
|---|---|
| **概要 / 分析** | 期間ごとのリクエスト、トークン、キャッシュ、および費用の概要 |
| **ログ** | モデル、ステータス、トークン、コスト、レイテンシ、TTFT、およびリクエストの詳細 |
| **API Keys** | ステータス、サービスモード、有効期限、制限、およびキーの使用状況 |
| **請求** | 組織の残高、チャージ、取引、請求書 |

非ストリーミングのチャットコンプリートには `hostlinku.cost` が含まれます。ストリーミングSSEでは、チャンクごとのコストが保証されません。最終的なコストは「Logs/Analytics/Billing」で確認してください。`x-request-id` は、リクエストとログを関連付けるのに役立ちます。

<a id="isi-log-dan-retensi"></a>

<a id="ログ内容と保持"></a>

## ログの内容と保存期間

ボディロギングは**デフォルトで無効**です。管理者が有効にした場合、内容はサイズ制限が設けられ、認証情報フィールドはフィルタリングされます。ボディの保持期間はデフォルトで14日間です。使用状況／トランザクションのメタデータは引き続き保存されます。[プライバシー](/ja/legals/privacy-policy)を参照してください。

ヘルスプローブの生データは、デフォルトで**30日間**保存され、その後定期的に削除されます。リクエストの内容については、別途**14日間**の保存期間が設けられています。利用状況およびトランザクションのメタデータは引き続き保存されます。

<a id="biaya-historis"></a>

<a id="過去の料金"></a>

## 過去の費用

請求総額については、ログに記録された値をそのまま使用します。一部の分析詳細については、現在のトークンおよび料金に基づいて再計算されます。再請求が行われない場合、詳細情報は過去の合計額と異なる場合があります。

<a id="arti-429-dan-402"></a>

<a id="429と402の意味"></a>

## 429および402の意味

| コード | 意味 | アクション |
|---|---|---|
| `429 RATE_LIMITED` | リクエスト数の制限を超えました | リセット待機、バックオフ、競合の低減 |
| `402 PAYMENT_REQUIRED` | 利用可能な残高が不足しているか、キーの制限に達しています | メッセージを確認してください：残高のチャージ、リセットの待機、または適切な制限の変更 |
