## 1. Encryption and secure storage

Communication with the website, Console, and Hostlinku API is protected by **HTTPS (TLS)**. Credentials are protected according to their type:

- **Account passwords** are not stored in plaintext.
- **Customer API keys** are stored as **SHA-256** hashes for verification, not as keys that can be displayed.
- **Integration credentials**, including the upstream provider key and SSO secret, are encrypted using **AES-256-GCM** at the application level. The encryption key is derived from the application environment configuration, separate from the encrypted values in the database.

## 2. Account Authentication

The Hostlinku identity service is available via `auth2.hostlinku.com`, using the industry-standard identity federation protocols **OpenID Connect (OIDC)** and **OAuth 2.0**. The authorization flow uses **PKCE S256**. Login, email verification, and enabled SSO options are managed through this service.

<a id="passkey-dan-multi-factor-authentication-mfa"></a>

<a id="passkeys-and-multi-factor-authentication-mfa"></a>

### Passkey and Multi-Factor Authentication (MFA)

In addition to email and password, the following authentication methods are available:

- **Passkey (FIDO2/WebAuthn):** passwordless authentication based on public-key cryptography. The private key is managed by the authenticator or passkey provider and is not sent to the server during authentication.
- **Authenticator (TOTP):** a time-based one-time code generated by an authenticator app.
- **Recovery codes:** one-time backup codes used to restore access when the primary authentication factor is unavailable.

All authentication methods can be managed through **Console → Settings → Security**. Select **Add passkey** to register a passkey, then select the button to sign in using the passkey on the login page. Store the recovery code in a secure location that remains accessible when needed.

<a id="sesi-console"></a>

<a id="console-sessions"></a>

### Console Session

Console validates access through a session stored on the server, using the **`hl_sid`** cookie. Upon login, the backend also issues a JWT cookie **`hl_session`**. Both are configured with **`HttpOnly`** and **`SameSite=Lax`**; **`Secure`** is enabled when the backend is running in production mode.

`HttpOnly` restricts a page’s JavaScript access to cookies, `Secure` ensures cookies are sent only over HTTPS, and `SameSite=Lax` restricts the inclusion of cookies in cross-site requests.

Suspended accounts cannot log in or use the API.

## 3. Handling API keys

- The key is displayed in full only once when it is created and cannot be viewed again.
- A key has a Service Mode, expiration date, and credit limit; it can be disabled from the Console. The current form does not offer endpoint scope.
- When body logging is enabled, credential fields are filtered before being stored. Secrets in the prompt text are not automatically filtered.
- The upstream provider’s identity and upstream credentials are never sent to customers.

## 4. Isolation and access control

- Access to requests, logs, balances, and API keys is verified based on the user, organization, and authorized roles.
- Admin functions are restricted to the admin role, and any changes to sensitive settings—including enabling body logging and adjusting balances—are recorded in the audit log.
- Request and response content is not stored by default; if body logging is enabled, the content is automatically deleted according to the retention period. See [Privacy Policy](/en/legals/privacy-policy).

<a id="perlindungan"></a>

<a id="5-perlindungan-layanan"></a>

## 5. Service Protection

- Public traffic passes through Cloudflare to mitigate bots and volumetric attacks.
- Shared usage quotas per organization and request limits per IP are described in [Usage & Limits](/en/usage-and-limits).
- Reserving a balance before a request is forwarded prevents excessive usage beyond the available balance.
- Model and upstream health monitoring is published on the [Status](https://status.hostlinku.com) page.

<a id="audit"></a>

## 6. Audit log

We log security events such as logins, logouts, registrations, API key creation and revocation, and setting changes, along with the time, IP address, and user agent. Secret values are never logged.

## 7. Shared Responsibility

<Callout title="Notes" type="note">

Account security also depends on you:

- Use strong and unique passwords;
- Store the API key on the server side, not in frontend code or a repository;
- Use a separate key per application or environment, set credit limits, and revoke unused keys;
- Monitor logs and transaction history in the console to detect unusual usage.

</Callout>

## 8. Incident Response

When a security incident occurs, we perform identification, containment, recovery, and evaluation. If the incident results in a failure to protect personal data, we notify affected users and the authorities in accordance with the provisions of the Personal Data Protection Act (PDP Act). If we detect a leaked API key, we may deactivate that key and notify its owner.

## 9. Reporting vulnerabilities

Submit a report to [halo@hostlinku.com](mailto:halo@hostlinku.com) with a description, reproduction steps, and the impact you’ve observed. We’ll confirm receipt within 5 business days.

To ensure testing remains secure:

- Test only with your own account and data;
- Do not access, modify, or delete other users’ data;
- Do not engage in denial-of-service attacks, spam, or social engineering against staff or users;
- Please give us a reasonable amount of time to make corrections before publishing your findings.

We will not take legal action against researchers who report in good faith and follow these guidelines.
