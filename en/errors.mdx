## Response formats

The error format depends on the endpoint. `error.message` explains the problem; use the HTTP status and error code/type for automated handling. Message language can vary by service.

**Chat Completions and general endpoints** use Hostlinku codes:

```json
{
  "status": "error",
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "The request body is invalid.",
    "details": {
      "issues": [{ "path": "messages", "message": "Array must contain at least 1 element(s)" }]
    }
  }
}
```

**Anthropic Messages** uses `error.type`, without a Hostlinku code in `error.code`:

```json
{"type":"error","error":{"type":"invalid_request_error","message":"The request body is invalid."}}
```

**OpenAI Responses** uses the OpenAI format with mapped codes:

```json
{"error":{"message":"The request body is invalid.","type":"invalid_request_error","param":null,"code":"invalid_request"}}
```

Responses mapping examples: `UNAUTHORIZED` → `invalid_api_key`, `MODEL_NOT_FOUND` → `model_not_found`, and 429 errors → `rate_limit_exceeded`. Messages groups these through types such as `authentication_error`, `not_found_error`, and `rate_limit_error`.

Schema validation returns **422** for Chat Completions and **400** for Messages/Responses. `error.details` is optional; `error.details.issues` identifies invalid fields. Errors before a protocol handler, such as body parsing, request rate limiting, or unknown paths, can use the general Hostlinku format.

## Hostlinku codes

This table covers Hostlinku codes for gateway and general endpoints. Messages/Responses use the mapping above; other account or payment codes can appear on their respective endpoints.

| HTTP | Code | Meaning and action |
|---|---|---|
| 400 | `BAD_REQUEST` | Invalid JSON/parameters, including the model output limit. Correct the request. |
| 400 | `MODEL_NOT_IN_SERVICE_MODE` | The model is unavailable in the key's Service Mode. Choose from `GET /v1/models` using the same key. |
| 400 | `UPSTREAM_REJECTED` | The provider rejected the request. Read the sanitized reason and correct the input. |
| 401 | `UNAUTHORIZED` | Missing, invalid, revoked, or expired authentication. Check the key. |
| 402 | `PAYMENT_REQUIRED` | Insufficient available balance or key spending limit reached. Check [Billing](/en/billing). |
| 403 | `FORBIDDEN` | Access denied. Check account permissions. |
| 404 | `NOT_FOUND` | Path or resource unavailable. Check the URL and ID. |
| 404 | `MODEL_NOT_FOUND` | Unknown model slug. Check the catalog. |
| 405 | `METHOD_NOT_ALLOWED` | Incorrect HTTP method. Use a method from the `Allow` header. |
| 413 | `BAD_REQUEST` | Payload too large. Reduce the body size. |
| 415 | `BAD_REQUEST` | Unsupported body encoding/charset. Check the body format. |
| 422 | `VALIDATION_FAILED` | Body/query validation failed. Correct fields in `error.details.issues`. |
| 429 | `RATE_LIMITED` | Organization quota per Service Mode or endpoint/IP limit reached; upstream can also return rate limiting. Wait and reduce concurrency. |
| 429 | `MODEL_AT_CAPACITY` | The provider's model capacity is full. Follow retry advice. |
| 429 | `MODEL_COOLDOWN` | Model deployments are recovering after failures. Follow retry advice. |
| 500 | `INTERNAL` | Internal error. Save request details and report repeated failures. |
| 503 | `MODEL_UNAVAILABLE` | Model unavailable or deprecated. Check the catalog and replacements; retry if the outage is temporary. |
| 503 | `PROVIDER_UNAVAILABLE` | Provider route unavailable. Retry with a delay and a limited attempt count. |
| 503 | `UPSTREAM_ERROR` | Upstream failure. Retry with a delay and a limited attempt count. |
| 503 | `UPSTREAM_TIMEOUT` | Upstream timed out. Retry with a delay and a limited attempt count. |
| 503 | `UPSTREAM_UNREACHABLE` | Upstream unreachable. Retry with a delay and a limited attempt count. |

### Console and checkout

These account/checkout codes are separate from the `/v1/*` inference error contract:

| HTTP | Code | Meaning and action |
|---|---|---|
| 403 | `API_KEY_NOT_ALLOWED` | An API key was used on a Console account endpoint. Use a Console login session. |
| 409 | `CONFLICT` | The operation conflicts with the current state. Reload the state before retrying. |
| 424 | `CHECKOUT_FAILED` | The provider failed to create an invoice. Read the message and check the transaction before creating another. |
| 424 | `BANK_BUSY` | The iPaymu bank/channel is busy. Choose another bank offered by checkout. |

## Retry and streaming

When present, `Retry-After` gives the wait in seconds and `retry-after-ms` gives milliseconds. Otherwise, use exponential backoff with jitter and a limited attempt count. Adding keys or member accounts within the same organization does not increase the shared quota; see [Usage & Limits](/en/usage-and-limits).

Once SSE begins, failures are sent as error events within the stream; the initial HTTP status does not change. Chat Completions example:

```text
data: {"error":{"code":"MODEL_AT_CAPACITY","message":"The model is at capacity right now. Please retry shortly.","type":"upstream_error","retry_after_ms":4000}}
```

The gateway does not append `[DONE]` after a stream failure it handles. A connection can also close without an error event. `[DONE]` or connection closure alone does not establish success; check error events and request logs. See [Messages](/en/anthropic-messages) and [Responses](/en/responses) for their event formats.

When reporting, include `x-request-id` if available, time, endpoint, model, HTTP status, and the error body without secrets. See [Support](/en/support).
